# Migration report: MongoDB app to PostgreSQL

Source of truth for business behaviour: the old `TheBetFundrAppBackend` (MongoDB, Express 4).
Source of truth for architecture: `core-api postgres` (Express 5, Sequelize, layered).
The old code was never modified: all work is in this separate project.

**Status:** the application builds, lints clean, migrates, starts, and passes **100 of 100 automated tests** against a real PostgreSQL 16
(9 wallet-integrity, 41 financial, 50 HTTP/API). Several decisions about financial behaviour need **your confirmation**: see section 5.

---

## 1. What the old application actually was

A bridge between mobile money and betting accounts:

1. A customer pays through mobile money (QOS for MTN/MOOV, or Fedapay), optionally topped up from an in-app wallet (`bonusBalance`).
2. The backend credits the customer's betting account through the **mobcash cashdesk API**.
3. Withdrawals are requested either from the wallet or by redeeming a cashdesk withdrawal code, then paid out by staff.
4. Referrers earn a wallet bonus on their referrals' deposits. Users can send wallet money to each other and create QR codes that anyone can pay without logging in.
5. Around that: a social feed, admin-curated predictions, a football-data cache, push notifications, socket.io.

Money was stored as JavaScript floats, history lived in arrays inside user and admin documents (three copies of every transaction),
and one global `transactionInProgress` variable "protected" all money movement.

## 2. Architecture changes

| Before | After |
|---|---|
| Route handlers of 300 to 1,450 lines containing everything | routes, middleware, controllers (HTTP only), services (logic), repositories (SQL), providers (external systems) |
| Three near-identical deposit implementations (about 3,000 lines) | one `deposit.service` with three modes (mobile money, Fedapay, wallet) |
| Global `transactionInProgress` flag | row-level locking, guarded updates, idempotency keys (see 4) |
| Mongoose, `express-validator` | Sequelize + SQL migrations, Joi |
| Secrets in source | environment only; secrets removed from logs; none copied into the new project |
| `console.log` | structured pino logging with redaction of passwords, PINs, tokens, phone numbers |
| No tests | 100 tests including concurrency, rollback and idempotency |

## 3. MongoDB to PostgreSQL conversions

| MongoDB | PostgreSQL |
|---|---|
| `users` | `users` (money as NUMERIC, role column, hashes renamed) |
| `users.transactionHistory[]`, `pendingDeposit[]`, `bonus[]`, `admin.transactionHistory[]`, `admin.pendingTransactions[]` | **one** `transactions` table: one row per user-visible transaction. "Pending" is a status, not a copy |
| (no ledger) | `ledger_entries`: append-only record of every wallet change, with balance after |
| `admin` document (switches, counters, delete requests) | `platform_settings` (single row), `account_deletion_requests`, `users.role = 'admin'` |
| `subadmins` | `users.role = 'subadmin'` (the collection had no routes using it) |
| `users.supplementaryBetId[]` | `user_bet_ids` |
| `users.referrals[]` (emails) | `users.referrer_id` foreign key |
| `users.followers[]/following[]` | `follows` |
| `posts.likes[]/views[]/saves[]/media[]`, `comments`, `notifications` | `post_likes`, `post_views`, `post_saves`, `post_media`, `comments`, `notifications` (counts are computed, so they cannot drift) |
| `QrCodeDeposit` | `qr_code_deposits` |
| `MatchPrediction` + `SecondMatchPrediction` (identical) | `match_predictions` with `list_no` 1 or 2 |
| `League`, `Team` (predictions) | `prediction_leagues`, `prediction_teams` |
| `Fixtures`, `Leagues`, `Standings`, `Events`, `Lineup`, `Statistics` | `api_cache(kind, cache_key, payload JSONB, fetched_at)` |
| `countDocuments()`, `populate()`, `$push`, positional `$` update | SQL counts, joins / batched lookups, rows, JSONB rewrite |
| ObjectId | UUID (generated by the database) |
| (new) | `payment_events`: log of provider callbacks |

Integrity features added in the schema: foreign keys everywhere, 27 indexes (incl. partial and unique), `CHECK` constraints on every balance and amount,
case-insensitive unique email and tag, a unique `(user_id, idempotency_key)`, a unique `(reference, funding_type)`, and two triggers
(status transitions, append-only ledger). The full schema is in `docs/schema.sql`; migrations are `migrations/001..005`, each with a tested down script.

## 4. Financial integrity: how it works and the evidence

**Rules that hold on every path**

- **Hold first.** The wallet part of a deposit or withdrawal is debited *inside the same database transaction* that creates the Pending transaction. No provider call happens while a database transaction is open.
- **Refund only on certainty.** A hold is returned only when the payment provider *definitely* failed. A timeout or unreadable answer leaves the transaction `Pending` with funds held and a flag for reconciliation. The cashdesk is never retried automatically.
- **Credit the cashdesk at most once.** Only the caller that flips `payment_confirmation` from Pending to Successful may call the cashdesk. Webhook, poller and original request can race safely.
- **Settle once.** `Pending -> Successful/Failed` uses a guarded UPDATE; the referral bonus and counters are written in the same transaction, so a second settlement attempt does nothing.
- **No overdraft, ever.** One SQL statement checks and applies each balance change (`WHERE bonus_balance + delta >= 0`); `CHECK (bonus_balance >= 0)` backs it up in the database itself.
- **Transfers.** Both wallets, both history rows and both ledger entries change in one transaction; rows are locked in id order so opposite transfers cannot deadlock.
- **Provider callbacks are hints, not facts.** A callback is authenticated by a shared secret and only triggers a re-check with the provider.

**Tests that demonstrate it** (all against real PostgreSQL)

| Property | Test |
|---|---|
| No double spend | 25 concurrent debits of 10 against 100: exactly 10 succeed. Same for 10 concurrent deposits, 12 withdrawals, 20 transfers |
| No deadlock, money conserved | 50 simultaneous opposite transfers (A to B and B to A) all succeed and balances add up |
| Rollback | failure after the sender is debited leaves both wallets, history and ledger unchanged |
| Idempotency | same key twice, and 8 simultaneous identical requests: one transaction, one debit, one cashdesk call |
| Exactly-once credit | 3 simultaneous callbacks + 2 simultaneous finalizers: cashdesk called once, bonus paid once |
| Failure handling | provider failed: refunded once. Cashdesk rejected / unknown: stays Pending, **not** refunded, not retried |
| Callback not trusted | callback says SUCCESS, provider says FAILED: deposit fails. Forged callback for an unknown reference: nothing happens |
| Database as last defence | direct SQL setting a negative balance, editing the ledger, or moving a Successful transaction to Failed is refused |
| Ledger reconciles | after every scenario, each user's balance equals the sum of their ledger |

## 5. Ambiguities and decisions that need your confirmation

I did not invent financial rules. Where the old code was unclear I chose the safest reading, and I list it here so you can overrule it.

1. **The old code had provider calls stubbed out.** In the `/deposit` route the payment result was a hardcoded `{ status: 'SUCCESSFUL' }` and the cashdesk result a hardcoded `{ Success: true }`; `/withdrawal` returned a hardcoded `Summa: "500"`; most `rechargeAccount` / `withdrawFromAccount` calls were commented out; `/walletdeposit` never called the cashdesk at all. These look like test leftovers. **I implemented the real flow** (collect, then credit the cashdesk; redeem the code and read the amount), using the commented-out code and the one live call as the specification. *Please confirm that this is the intended production behaviour.*
2. **Fedapay deposits are never settled by this code**, in the old app or the new. They stay `Pending`. Something outside this repository must have completed them. *Decide where settlement lives (Fedapay webhook, admin panel, job).*
3. **There are no admin or sub-admin endpoints in the old repo.** The admin panel almost certainly read and wrote the MongoDB database directly (e.g. to flip `isDepositsOpen`, resolve Pending transactions, process deletion requests). **That panel must be pointed at PostgreSQL** (tables above) **or given an API.**
4. **Referral bonus** is 3% x 33% = **0.99% of every successful deposit**, as in the old code (not only the first deposit). Fractions are kept to 4 decimals; the old code used floats with unspecified rounding.
5. **Fedapay charge** is the amount less 1.8%, rounded, as before (configurable: `FEDAPAY_PROVIDER_FEE_PERCENT`).
6. **Five-minute duplicate rule** was enforced by the cashdesk (code 100337). It is still handled that way, and is now also checked up front so nobody is charged for a credit that would bounce.
7. **Cashdesk problems after money was taken** (codes 100337 / 100323, or unknown): transaction stays `Pending` with `custom_error_code` 300 / 301, exactly as the old app recorded them, and the wallet part is **not** refunded.
8. **Withdrawals end `Pending`** (staff pay out), for both wallet and account-code withdrawals, as the old data model implied.
9. **Maintenance switches** return 504 for deposits and 405 for withdrawals, as before.
10. **Reversals.** The old app had no reversal feature, so there is no `Reversed` status. The ledger can record refunds of holds; manual reversals would need a rule from you.
11. **Assumed values** (not specified in the old code): reset codes are 6 digits, valid 15 minutes, locked after 5 wrong tries; PIN is 4 to 8 digits; password minimum 6 (old check was 4 although its message said 6); JWT lifetime 30 days (old tokens never expired); QR code can be paid once.

## 6. Security problems found in the old code (and fixed, not ported)

| Old behaviour | Now |
|---|---|
| Hardcoded admin account auto-created for a fixed email + password | removed; admin only via `npm run seed:admin` with your own credentials. **Registering the old credentials makes an ordinary user (tested)** |
| `resetPasswordForLoggedInUser2` reset *any* account's password with no proof (account takeover) | requires the emailed one-time code, bound to the purpose, single-use, 5-try lockout. **Attack tested and refused** |
| Money routes took the user id from the request body (anyone could spend anyone's wallet) | identity always comes from the verified token. **Attack tested** |
| Transfer amount unvalidated: a negative amount stole money | amounts validated strictly (positive, 2 decimals, no exponent notation). **Tested** |
| Global lock could stay stuck forever after one error; also serialised every user | removed, replaced by row-level locking |
| Password and PIN hashes, full history, even other users' data returned to clients | explicit serializers; **tests assert no hash ever appears in a response** |
| Any logged-in user could create or delete leagues, teams and predictions | admin only |
| No ownership checks on posts and comments | owner (or post owner for comment deletion) only |
| JWT without expiry; "single session" never enforced | 30-day expiry; a new sign-in invalidates the old device session |
| Sports API key hardcoded in source; Firebase service-account file in the repo | environment variables only; neither copied |
| Provider "callback" trusted blindly and held in process memory (breaks on more than one server) | secret-protected, re-verified with the provider, database-backed |
| User-controlled values placed into email HTML | escaped |
| Uploads accepted by file name or declared type | images are fully re-encoded (also strips hidden payloads); fake images refused; size limits |
| Error responses included raw error objects | generic messages; details only in logs |

> **Please rotate** the hardcoded admin password, the API-Sports key, the Firebase service account and your JWT secret, because they have lived in a repository.

## 7. Changes the mobile app must handle

Paths and success shapes are kept. These behaviours changed on purpose:

- **Password reset** (`resetPasswordForLoggedInUser2`) now needs `{ email, pin: <emailed code>, password }`. The app already has the code from the previous step; it must send it again.
- **`changeUserPin`** now needs `{ pin, code }` (code from `requestPin`). **`setPin`** works once.
- **`walletSend`** takes `recipientId` (or `recipientid`); the sender is the signed-in user; the body `id` is ignored.
- **`getTotalReferral`** no longer returns referrals' email addresses.
- Duplicate-payment refusal is HTTP 409 with `success: 300`. QR already used or expired is 400.
- Money values are JSON numbers, as before; storage is exact decimal.
- Social list responses follow the old structure (post with `user`, `likes`, `views`, `saves`, counts), but I could not verify every field the app reads. **Test the feed screens.**
- New optional `Idempotency-Key` header on money requests (recommended).

## 9. Test results

`npm test` -> **100 passed, 0 failed** (about 13 s). `npm run lint` -> clean. Also run for real: clean install, `migrate up` on an empty database, `migrate down` of all
migrations and back up, `seed:admin` twice (idempotent), boot of `server.js`, live requests (health, register, admin login, 403 without a token, security headers), fail-fast on missing config, graceful SIGTERM shutdown.

**Not executed, and why**

- **Real payment providers** (QOS, Fedapay, mobcash), **SES email, Expo push, Firebase storage, Rekognition, API-Sports**: no credentials or sandbox access. The adapters are written from the old code but only exercised through test doubles. **Run a sandbox transaction through each before go-live.**
- **socket.io**: written (token-authenticated, per-user rooms) but not covered by an automated test.
- **Load and performance testing**, and behaviour on a PostgreSQL other than 16.
- **Migrating existing data** from MongoDB (see below).
- Flows that depend on the real mobile app (response shapes of social endpoints, see 7).

## 10. Unresolved issues and limitations

1. **No data-migration script.** Schema and code are migrated; moving existing MongoDB documents is not. Section 3 is the field mapping. Embedded transaction arrays become `transactions` rows; each user's `bonusBalance` should be loaded through a ledger `adjustment` entry so the ledger reconciles from day one. I did not write it because I could not test it against your real data.
2. Items 1 to 3 of section 5 (stubbed providers, Fedapay settlement, admin panel).
3. No automatic reconciliation job: `Pending` transactions whose provider outcome was unknown must be resolved by staff or a job you add. The state is queryable (`status = 'Pending'`, `metadata.cashdesk`).
4. Email-based flows reveal whether an email exists (501 vs 502) because the app depends on those codes; they are rate limited.
5. Uploaded files use local disk by default; set `STORAGE_DRIVER=firebase` for production, which keeps your existing bucket.
6. `bcryptjs` is used (compatible with existing `$2a$` hashes and needs no native build), where the reference template uses native `bcrypt`.
